# 提案：軟體工程師的一天改以「ticket」為主線（已核准（HP9），已實作 v0.10）

依據：使用者於 2026-10-22 提供的工作描述（7 點，摘要見文末）。

## 和現在的差別
目前的版本是一串彼此獨立的事件，玩家看不到「一個需求從開發到上線」的過程。改版後，一整天都圍繞同一張 ticket 前進：

> 領 ticket → 開發 → 寫單元測試 → 本機測試 → 主管 review（可能被退回）→ 部署到開發環境並再測試 → 部署到正式環境

中間會被其他工作打斷：線上告警、review 別人的 PR、技術分享會、需求變更、新人提問。

- **刪除的事件**：事後檢討報告、下班前的工單、測試環境出錯。更新 ticket 狀態會併進「部署」事件。
- **退回的條件**：寫單元測試時選了「只測正常情況，趕進度」，或者開發時選了「先求能動」，「主管 review 退回」就會出現。原因會寫明是邏輯錯誤、效能不佳或測試不足，玩家要選擇重寫或補測試，都要花時間。這延續「每個選擇都有代價」的原則：趕進度的代價在下午才出現。
- **review 別人的 PR**：快速核准不再觸發「測試環境出錯」，改成在部署事件中多一個風險結果（結果文字不同，加上信任 −5）。
- **時間壓力**：寫測試每局都會出現，就不需要「倒數隨事件增減」，HP8 的傍晚壓力問題自然解決。倒數時間實作時重新計算，再給你看。

## 使用者描述摘要（2026-10-22）
1. 每天早上 5 分鐘站會（Scrum），讓團隊了解彼此在做什麼。
2. PM 開 ticket，工程師照 ticket 開發。開發要滿足需求、符合公司規範、寫單元測試、適用不同情境、不破壞現有系統。
3. ticket 有期限，要在期限內完成開發、測試、通過審核、部署開發環境、再測試、部署正式環境。
4. 本機測試完才給主管 review。邏輯錯誤、效能不佳或單元測試不佳，程式會被退回重寫。
5. 午餐後如果沒有例行會議，就繼續早上的工作。
6. 每月有幾次技術分享會，講者可能是內部工程師或外部講師。
7. 可能要 review 別人的 PR，或解決不熟悉的 issue。

## HP9 決定（2026-10-22）
- 保留三件舊事件：事後檢討報告、下班前的工單、測試環境出錯；事件上限 12 → 14。
- 為了放進 14 件，「開發 ticket」不獨立成事件：站會領 ticket 後的選項就是開發怎麼開始（先問清楚需求／直接開工「先求能動」）。上午群組維持「事後檢討報告」＋「同事的 PR」。
- 「測試環境出錯」仍是快速核准 PR 後的條件事件，但「寫測試」小遊戲移到每局都有的「寫單元測試」事件；測試環境出錯改回一般事件（可附查資料或不附）。
- HP8 照建議：倒數可隨條件事件增減（基本值＋該事件出現時加時），驗證器兩種情況都檢查「做得完、有壓力」。其他三項（第 1 行做成卡、上午 30→35 或重算、印表機「有人找你」）照做。
- 使用者描述記入 `practitionerFeedback`；軟體工程師小遊戲拿掉「內容待從業者審查」徽章。
